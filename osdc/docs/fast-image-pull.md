# FastImagePull (SOCI parallel pull)

Cutting cold-node container image pull time on Karpenter runner nodes.

## The problem

A fresh Karpenter node cannot run a job until it has pulled its images. Across a
prod cluster that is roughly 90 TB/day of image layers against ~1,516 node
creations/day (`docs/current_runner_load_distribution.md`) — on the order of tens
of GB per cold node, most of it PyTorch CI toolchain images
(`pytorch/pytorch-linux-*`, `pytorch/almalinux-builder-cuda*`), not the ARC
runner image itself, which is a few hundred MB.

That pull time is billed node time. The `image-cache-janitor` DaemonSet keeps a
~500 GiB node-local cache, so a *warm* node re-pulls nothing — the cost is
entirely in cold starts, and node-compactor's aggressive consolidation means
cold starts are frequent by design.

Note this is a **latency and node-hours** problem, not a bandwidth one. Since
`docs/s3-gateway-endpoint.md` those bytes are free.

## The fix

nodeadm's `FastImagePull` feature gate switches containerd to the SOCI
snapshotter in **parallel pull and unpack** mode: multiple concurrent HTTP
connections per layer, and layer unpacking spread across cores instead of one
layer at a time.

```yaml
apiVersion: node.eks.aws/v1alpha1
kind: NodeConfig
spec:
  featureGates:
    FastImagePull: true
```

Emitted into every EC2NodeClass `userData` by
`modules/nodepools/scripts/python/generate_nodepools.py`, driven by
`nodepools.fast_image_pull` in `clusters.yaml`.

AWS measured ~60% faster pulls on a 10 GB Deep Learning Container image.
AppsFlyer reported an 82% cold-start reduction running GitHub Actions runners on
EKS — the same workload shape as OSDC.

### Why not lazy loading

SOCI's other mode fetches byte ranges on demand instead of whole layers. It is
the wrong tool here, and the two modes are mutually exclusive:

- It needs a SOCI index per image. Index v1 discovered it via the OCI Referrers
  API; index v2 (default since soci-snapshotter v0.10.0) bundles it into an OCI
  Image Index, which **changes the image digest** and requires a repush.
- The images that matter are built by pytorch/pytorch's `docker-builds`
  workflow, not by this repo. Indexing them is a cross-repo pipeline change.
- There is a measured crossover at ~80% access density: above it, a parallel
  full pull beats lazy loading. A compile job walking a CUDA toolchain image
  sits on the wrong side of that line.

Parallel pull needs none of this — it works on unmodified standard OCI images.

## Configuration

Cluster-level, in `clusters.yaml`:

```yaml
meta-staging-aws-uw1:
  nodepools:
    fast_image_pull: true
```

Per-def override in a nodepool def, following the `node_compactor` idiom:

```yaml
fleet:
  name: some-fleet
  fast_image_pull: true    # or false, to opt one fleet out
```

Currently enabled on `meta-staging-aws-uw1`, `-ue1`, and `-ue2` only. No prod
cluster has it until the staging soak says otherwise.

## Preconditions — all already satisfied

| Requirement | Status |
|---|---|
| Root volume ≥600 MiB/s | `generate_nodepools.py` sets gp3 `throughput: 1000`, `iops: 16000` for both CPU and GPU pools |
| Instance ≥2xlarge (gate is ignored below) | Smallest instance across all defs is `t4g.2xlarge`; everything else is 8xlarge+ |
| AL2023 AMI carrying the SOCI plumbing | Landed in amazon-eks-ami PR #2548, shipped ~v20260107. CPU pools use `alias: al2023@latest`; GPU pools glob `amazon-eks-node-al2023-x86_64-nvidia-*`. Both resolved to `v20260818` as of 2026-08-21 |
| SOCI state on fast storage | nodeadm mounts `/var/lib/soci-snapshotter-grpc` onto the instance store; `instanceStorePolicy: RAID0` is already set on the NVMe fleets (all GPU pools). CPU pools stay on gp3, which is above the throughput floor |

## Scope

- **CPU and GPU runner fleets** from `modules/nodepools`, `nodepools-h100`,
  `nodepools-b200` — these share `deploy.sh`, so the cluster flag covers them
  together.
- **BuildKit is not affected.** It runs on its own NodePools generated by
  `modules/buildkit/generated/nodepools.yaml`, entirely separate from these
  defs.
- **Custom-AMI fleets opt out automatically.** A def using `ami_selector_tags`
  (e.g. the ai-sandbox gVisor image) only moves when that AMI is rebuilt, so it
  may predate the gate — and nodeadm *rejects* an unknown feature gate, failing
  node bootstrap outright rather than degrading. Such a def must set
  `fast_image_pull: true` explicitly to opt back in.

## Trade-offs

The gate costs more CPU, memory, and EBS throughput *during* the pull — that is
the mechanism, not a side effect. On the packed CPU fleets, watch whether pull
bursts contend with running jobs; the fleets are large (8xlarge and up) so there
should be headroom, but it is the thing most likely to surprise.

## Rollout and measurement

1. Baseline before enabling. The kubelet ServiceMonitor is disabled under
   IPv6-only EKS, so `image_pull_duration_seconds` is not in Mimir — time a
   representative `crictl pull` on a staging node directly.
2. Deploy to `meta-staging-aws-uw1` and compare node-launch → first-job-started.
3. Soak, then ue1/ue2 staging, then reassess for prod.

Rollback is `fast_image_pull: false` and redeploy the nodepools module; existing
nodes keep their bootstrap config until they rotate.
