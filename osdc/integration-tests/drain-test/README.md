# OSDC drain/undrain slow test

This document describes the drain/undrain end-to-end test that runs as part of the OSDC pre-merge slow-test suite. For the CI orchestration and merge-gate mechanics, see [`osdc/docs/ci-pre-merge.md`](../../docs/ci-pre-merge.md).

## When it runs

The CI drain/undrain test runs only on `meta-staging-aws-uw1`. The reusable slow-test workflow skips the drain-test job for every other cluster. The Python controller accepts cluster IDs defined in `clusters.yaml` for direct script and `just drain-test` invocations. All cluster configuration, including probe targeting and desired runner limits, comes from `clusters.yaml` under `--root-dir` (the OSDC directory by default); there is no separate `--clusters-yaml` override. In all modes, including `--dry-run` and `--restore-only`, it rejects unknown clusters and validates runner configuration before making external calls. The `--restore-only` mode is used by CI's subsequent recovery step with the same Linux runner's saved recovery record. Operator recovery uses the separate `just resume-runners <cluster>` operations recipe.

Live execution, including `--restore-only`, is allowed only when the CI workflow sets `OSDC_DRAIN_TEST_LIVE=true`. The reusable workflow `_osdc-slow-tests.yml` sets this variable in the `drain-test` job's test and restore steps, so the supported call chain remains `osdc-pre-merge.yml` → `_osdc-slow-tests.yml` → `drain-test`. The controller checks only this opt-in variable before constructing the controller, registering cleanup, reading cluster configuration, or making external calls. Local real execution is rejected; local `--dry-run` and offline unit tests remain available. To run the real test manually, dispatch `osdc-pre-merge.yml` from the desired branch. There is no local override. This check prevents unsupported invocation; it is not a credential or authorization boundary.

All drain-test modes require organization-scoped runner registration: the selected `arc-runners` block must provide `github_config_url: https://github.com/<org>` (an optional trailing slash is accepted) and an explicit, nonempty `runner_group`. The URL and group use whole-block defaults fallback together; missing keys in a cluster override do not inherit individual defaults. Repository-scoped URLs such as `https://github.com/pytorch/pytorch-canary` are rejected rather than falling back to `default`, preserving group-based probe targeting and verification. The CLI validates this before constructing the controller, registering cleanup, stopping recorded drain writers, or making external calls, including in `--dry-run` and `--restore-only`; direct preparation repeats the validation before kubeconfig setup. If runner registration has been changed to an unsupported scope, operator recovery remains the separate `OSDC_UNTAINT_NODES=no just resume-runners meta-staging-aws-uw1` recipe.

The caller holds `osdc-staging` for the entire battery, and the drain-test job holds `osdc-tofu-meta-staging-aws-uw1` across both the test and its recovery step, with `cancel-in-progress: false`. The fixed canary branch is retained because supported executions are serialized by these existing Actions concurrency groups; no ConfigMap lock is used. Any future execution entry point must preserve that serialization and set `OSDC_DRAIN_TEST_LIVE=true` in the workflow step that invokes the controller.

## Controller behavior

The controller runs on a GitHub-hosted runner and creates a temporary PR on the fixed `osdc-drain-test-meta-staging-aws-uw1` branch in `pytorch/pytorch-canary`; workflow names and PR titles retain a unique run key. Only that branch's workflows are replaced. Before reclaiming it, startup cleanup reads all pages of candidate runs and the open PRs. It selects runs whose names match the drain-test naming convention; unrelated workflow runs are logged and ignored regardless of whether they are queued, in progress, or completed. Ignoring those runs does not prevent closing recognized canary PRs or deleting the temporary branch. Every open PR title must match the drain-test naming convention; an unrecognized PR stops startup before any cleanup writes, limit repair, or canary creation. The internal cleanup helper requires callers to supply only selected canary runs and validates all supplied runs and PRs before cancelling runs, closing PRs, or deleting the ref. An accidentally supplied unrecognized resource is rejected before any cleanup writes. A ref left before PR creation can still be reclaimed. Probes are pinned to the staging cluster's configured `arc-runners.runner_group` and a label built from the configured `arc-runners.runner_name_prefix` plus runner definition name `l-x86iamx-8-16`. Before creating probes, preflight compares live limits with `runner_max_map.py`. Any mismatch triggers `just resume-runners` followed by complete-map verification, including region-excluded zeros; matching limits need no repair. A recovery record is written before startup repair and reused for the later drain, so failed or cancelled repair can hand off to the CI recovery step even on a fresh run attempt. Startup repair preserves existing refresh taints. Failed repair, missing/unexpected scale sets, and a disabled/missing probe scale set still stop the test before canary creation.

One in-flight job waits for a unique marker in its PR body. The controller starts `just drain-runners` in the background, waits for all live runner limits and all listener advertised capacities to become zero, then releases that job. It must succeed normally. Three dependent jobs then queue. The controller checks that none is assigned a runner, that all live runner limits remain zero, and that every expected scale set has a Ready listener with valid zero advertised-capacity metrics. Each attempt checks all listeners. The phase returns immediately after one complete successful check; there is no minimum observation window or subsequent stability check. Unavailable evidence is retried every 10 seconds within a fixed internal `OBSERVE_TIMEOUT = 120` second total budget, also bounded by the remaining main-flow budget. Retries share this deadline; missing metrics never count as zero capacity. Confirmed job assignments or completions, nonzero runner limits, and nonzero advertised capacities fail immediately. The observation timeout is not exposed as a CLI option. After this check passes, the controller adds refresh taints and records node UIDs. It then runs `just resume-runners` with `OSDC_UNTAINT_NODES=no`, requiring the complete configured limit map to be restored, including region-excluded zeros. Recorded nodes that survive must retain `deploy.osdc.io/refresh-pending=true:NoSchedule`, checked immediately after resume and again after the held jobs complete. Recycled nodes are allowed; if no nodes remain to verify, the controller reports the missing live taint coverage and continues capacity/job recovery. All original held jobs must subsequently succeed on the configured runner group with unchanged job IDs and verified pod placements.

Each held job starts in `Wait for controller release`, a bounded PR-body polling step. While it waits, the controller matches the original GitHub job's `runner_name` to the runner pod in `arc-runners`, verifies the scale-set label against the selected AutoscalingRunnerSet metadata name (which can differ from its GitHub runner label), and finds its workflow pod via the hooks' `runner-pod` label and `job` container. It records both pod UIDs and their node UIDs; neither pod may use a recorded stale node UID. Missing/ambiguous pods, unscheduled pods, or unavailable node evidence are retried within the completion deadline and cannot count as success. Only after verifying placement and surviving nodes' refresh taints does the controller write that probe's run-key/matrix-specific release marker. Each probe is released independently so a small runner limit does not require all three jobs to run simultaneously. Release markers accumulate, and saved placement evidence allows retrying an uncertain PR update even if the job has already completed and its pods have disappeared. After release, the original runner identity must remain unchanged. Seeing an unrelated new node is not acceptance evidence, and creating a new node is not mandatory if suitable untainted capacity already exists.

The test works around [ARC #4715](https://github.com/actions/actions-runner-controller/issues/4715), where jobs queued at capacity zero can remain stuck after restoration. After resume, the controller may submit up to eight lightweight `drain-wakeup` traffic pulses, separated by at least 15 seconds after each confirmed write, stopping once any original probe is assigned. It rechecks restored limits and positive probe-listener capacity before each send or retry. A local positive-capacity metric does not prove that the broker has already received the updated capacity: an early pulse can enter the queue while an older zero-capacity long poll is still in flight. Further bounded pulses avoid relying on that first pulse; exhausting the pulse limit does not extend the shared completion deadline. Each logical pulse retains its parent, tree and target commit. After an uncertain branch update, a retry reads HEAD: an already-applied target succeeds without another write, an unchanged parent allows retrying the same target, and an unexpected branch change aborts rather than overwriting it. Unconfirmed object-creation requests may leave unreachable Git objects, but retries do not publish an extra commit for an ambiguously successful ref update. Wakeups are not used during initial startup, drain, the held-job drain check, cleanup, or `--restore-only`. Remove the workaround when the upstream issue is resolved and verified.

The controller supplies queue/start and completion deadlines (30 minutes each), a drain-convergence deadline (5 minutes), and a shared 75-minute main-flow budget that also bounds CLI/API calls, polling, and metric scrapes. The probes have no warm pool in uw1, and the existing capacity policy is unchanged: fresh-job sharding means even group-pinned jobs may need to age approximately 15 minutes before capacity is provisioned. The longer deadlines leave time for node provisioning, runner registration, and container startup after that threshold. These are upper limits; each wait finishes as soon as its condition is met. Additional runtime consumes the shared `osdc-staging` lock; budget the normal start/completion waits rather than treating this as a quick smoke test. Controller cleanup has a separate 10-minute budget. The CI test step is capped at 90 minutes (75 main flow + 10 cleanup + 5 margin), with an 11-minute same-job recovery step whose controller has a 10-minute total budget, including preparation and retries. Checkout, toolchain setup, and AWS credentials have no separate cap; the job is capped at 120 minutes. The slow-test job timeout critical path is 270 minutes (`load-test 120 + max(compactor 30, janitor 30) + drain-test 120`); typical durations and throughput estimates still require live measurements.

Each listener-metrics batch has an independent cancellation flag. If a batch is abandoned by an error, timeout, or signal, queued scrapes are cancelled and running workers terminate and reap their own `kubectl` process groups. Workers check cancellation between short subprocess waits without resetting the command timeout or extending the captured controller deadline; process teardown also stays within that deadline. Controller cleanup can proceed without joining the metrics pool, while workers finish their bounded teardown. A subsequent observation uses a fresh cancellation flag. Missing or cancelled metrics remain errors and are never interpreted as zero capacity.

The controller runs the test with `--defer-recovery`: the normal test still performs undrain and verifies the original jobs, and successful tests clean owned original/wakeup runs and the temporary PR/ref in the test step, checking resource identities before cleanup writes. On failure, timeout, or cancellation, cleanup only stops drain writers and returns, leaving cluster recovery to the following step. Canary resources may remain; the next test calls `cleanup_stale_canary()` before creating new probes. Pending/running canary jobs can consume resources until then, and no next run means no automatic reclamation. Inline recovery and CI restore-only each allow up to three total recovery attempts within their remaining budgets; the `atexit` fallback shares that deadline and attempt count. CI keeps the test job cancellable and attempts restoration in a subsequent `always()` step, with no additional signal job or external controller. The ten-minute restore-only budget includes preparation, stopping surviving drain writers, restoration, verification, and retries; the budget is sized for at least one complete attempt. This is a time budget, not measured staging recovery time. GitHub's approximately five-minute cancellation deadline starts with cancellation, so stopping the test and starting recovery consume part of that window; an eleven-minute step cap does not extend it. Forced termination or runner loss can interrupt recovery; after cancellation, verify live runner limits and refresh taints, and use `just resume-runners meta-staging-aws-uw1` with explicit `OSDC_UNTAINT_NODES=no` if needed.

## Offline checks

These commands need no AWS/Kubernetes/GitHub credentials or API calls:

```bash
cd osdc
uv run --frozen --offline pytest integration-tests/drain-test/scripts/python -v
just drain-test meta-staging-aws-uw1 --dry-run
```

The controller sets `OSDC_TAINT_NODES=no` during drain so taints cannot hide the historical zero-limit capacity-monitor bug, and `OSDC_UNTAINT_NODES=no` during undrain and recovery to verify taint preservation. Recipe and manual undrain defaults are unchanged. Normal cleanup and failure/timeout/cancellation recovery leave every refresh taint in place, including test-added taints, so old nodes remain stale until naturally recycled. There is no taint-removal path or taint-ownership record. The saved recovery record identifies the cluster and drain process token only. Recovery does not wait for probe placement, job completion, or new nodes. Operational recipes and `osdc-drain.yml` / `osdc-undrain.yml` remain unchanged from main; the controller explicitly overrides their environment-variable defaults.

## Live acceptance

Live acceptance requires authorized staging access and the existing `CANARY_GITHUB_TOKEN` (canary contents/workflows and PR writes, Actions read/cancel):

1. Dispatch `osdc-pre-merge.yml` from the test branch; the drain/undrain slow test must pass. Record all three original held job IDs, their runner/workflow pod UIDs and node UIDs, and the stale-node baseline. At least one acceptance run must observe surviving stale nodes retaining their taints while the probes run elsewhere. An empty or fully recycled baseline is reported as missing live taint coverage, not proof of the stale-node scenario.
2. Cancel a normal run after zero limits are observed, record the cancellation-to-recovery-start and recovery durations, then verify that all configured runner limits are restored and all refresh taints, including test-added taints, are preserved on surviving nodes. If the process/step is forcibly killed before cleanup completes, recover manually with `OSDC_UNTAINT_NODES=no just resume-runners meta-staging-aws-uw1`, and record that the cancellation acceptance remains unmet. Clearing taints is a separate, explicit operator choice.

A manual dispatch deploys the chosen branch to shared staging, holds the staging lock for the full battery, and can replace a pending merge-queue invocation. Coordinate live acceptance with maintainers; offline unit tests cannot establish it.
